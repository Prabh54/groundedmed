# Architecture

Version: 1 (architecture review, 2026-10-21). Decisions referenced as ADR-nnn are in DECISIONS.md.
No implementation exists yet; this is the design the milestones build.

## Principle
Keep production compute lightweight.
Use hosted model inference.
Keep evaluation reproducible and mostly offline.
Prefer one obvious way to do each thing over configurable flexibility.

## 0. Component and provider summary

| Layer | Choice | Why it is simpler than the obvious alternative |
|---|---|---|
| Language/tooling | Python 3.12, `uv`, `ruff`, `pytest` | One tool (`uv`) replaces venv + pip + lockfile management. |
| API | FastAPI + Uvicorn | Typed request/response models and OpenAPI docs come free; no extra validation layer. |
| Agent graph | LangGraph `StateGraph`, 4 fixed nodes | Explicit nodes/edges instead of a hand-rolled state machine or an open-ended agent loop. |
| Vector store | Supabase Postgres + pgvector, exact search | One database holds text, metadata and vectors; at 2,500 rows an exact scan needs no index tuning. |
| Embeddings | Voyage `voyage-4` (1,024 dims) | Hosted, inside the 200M-token free allocation; no model in our server's memory. |
| Reranker | Voyage `rerank-3` | Same vendor and key as embeddings; one account instead of two. |
| Runtime LLM | Claude Sonnet 5.5 (`claude-sonnet-5-5`) for all runtime nodes (ADR-022) | One model = one config, one price row, one failure mode. |
| LLM output | Anthropic structured outputs (`output_config.format`, JSON schema) | The API guarantees parseable JSON, so no retry-on-bad-JSON code. |
| Independent judge | Google Gemini, paid tier, offline only (ADR-014) | Different provider from the runtime critic by construction; never deployed. |
| Frontend | Next.js App Router + Tailwind, Vercel Hobby | Vercel is Next.js's native host: push to deploy, no server config. |
| Backend host | Railway Hobby | Deploys a Python service from the repo with no Dockerfile or VM management. |
| CI | GitHub Actions | Already where the code lives; free allowance covers this project. |

## 2. Data and database schema

### Source data (PubMedQA, profiled 2026-10-21)
Hugging Face `qiaojin/PubMedQA`, pinned to revision `9001f2853fb87cab8d220904e0de81ac6973b318`.
- `pqa_labeled`: 1,000 rows — `pubid`, `question`, `context{contexts, labels, meshes,
  reasoning_required_pred, reasoning_free_pred}`, `long_answer`, `final_decision`.
- `pqa_unlabeled`: 61,249 rows — same minus `final_decision` and the two `reasoning_*` fields.
- There is no title field. Questions are often the article title.

Field handling:

| Field | Indexed? | Use |
|---|---|---|
| `context.contexts` | YES (the only embedded text) | Evidence passage |
| `context.labels` (BACKGROUND, METHODS, RESULTS…) | Stored, not embedded | Section headings in the UI |
| `context.meshes` | Stored, not embedded | Distractor selection; topic chips in UI |
| `pubid` | Primary key | Citation ID and PubMed link |
| `question` | NEVER stored in the DB | Benchmark query only (manifests) |
| `long_answer` (conclusion) | NEVER | Not used anywhere at runtime |
| `final_decision` | NEVER in DB | Gold label in eval manifests only |
| `reasoning_required_pred`, `reasoning_free_pred` | NEVER | Dropped at load time (ADR-009) |

### Passage granularity (ADR-012)
One passage per paper: the whole conclusion-free context, sections joined in order.
Contexts are short (median ~200 words), so this avoids chunking, makes Hit@k a direct PMID match,
and gives one citation per paper. Citation ID format: `PMID:<pubid>`.

### Table `documents`
```sql
create extension if not exists vector;
create table documents (
  pmid            text primary key,          -- citation ID is 'PMID:' || pmid
  sections        jsonb not null,            -- [{"label":"BACKGROUND","text":"..."}, ...]
  passage         text not null,             -- exactly what was embedded
  meshes          text[] not null,
  content_sha256  text not null,             -- hash of passage, for leakage/reproducibility tests
  corpus_version  text not null,             -- e.g. 'v1-seed20261021'
  embedding_model text not null,             -- 'voyage-4'
  embedding       vector(1024) not null
);
```
No label, question, conclusion or split column exists, so retrieval cannot see them.
No `source` column either (ADR-026): only labeled papers can be gold, so knowing which papers are labeled
would be a retrieval shortcut. `source` stays in `corpus.jsonl`/`corpus.json` for auditing only, and a test
fails if runtime code under `backend/app/` mentions it.
The runtime connects with a read-only database role (`groundedmed_reader`: SELECT only, read-only
transactions, RLS select policy; Supabase API roles revoked — ADR-027); only `scripts/ingest.py` uses a write role.
No runtime writes: queries are logged to stdout, not the database.

## 3. Data ingestion flow

```
HF dataset @ pinned revision
  -> scripts/prepare_dataset.py
       - drop answer fields at load time (ADR-009)
       - split PQA-L: test 200 / dev 100 / reserve 700 (ADR-008, seed 20261021)
       - select ~1,500 PQA-U distractors by shared specific MeSH terms, excluding duplicates of PQA-L
       - write data/manifests/*.json (+ test manifest SHA-256) and data/corpus.jsonl
  -> leakage tests (pytest) on corpus.jsonl
  -> scripts/ingest.py
       - embed passages with voyage-4 (input_type=document), batched
       - cache embeddings locally keyed by (model, content_sha256) so re-runs cost nothing
       - upsert into `documents`; verify row count == manifest count
  -> leakage tests again against the database
```

## 4. Query, retrieval and reranking flow

`retrieve(query, k_candidates=20, k_final=5)`:
1. Embed the query with voyage-4 (`input_type=query`).
2. Exact cosine search in pgvector: top 20 candidates (no ANN index at this size).
3. Rerank the 20 with Voyage rerank-3 against the query.
4. Return the top 5 with `pmid`, passage, dense score, rerank score, ranks.

Baseline: `retrieve(question)` → evidence gate → one synthesis call → citation validator.

Agent (ADR-023): queries = the original question + the planner's 1–3 sub-queries → dense top 20 for each
(one Voyage embedding call per query: multi-input requests took 23–26 s on 2026-10-23, see M3-T7) → union, dedupe by PMID (up to ~80) → rerank the pool against
the original question → top 5.
Baseline and agent get the same number of passages (5), not necessarily the same passages: the planner
widens the candidate pool, and because the original question is always one of the queries, the pool always
contains the baseline's 20 candidates. Fixing the count keeps the A/B comparison about better evidence,
not more evidence (ADR-015).
`planner_added_evidence` = how many of the agent's final 5 were not in the baseline's top-20 candidates;
it is logged per answer and summarized in every eval run.

Hit@k is measured on the final top-5 list. Dense-only Hit@k (before rerank) is logged as a diagnostic.

## 5. Graph state

```python
class ResearchState(TypedDict):
    request_id: str
    mode: Literal["agent"]
    question: str
    subquestions: list[SubQuestion]          # planner output
    retrieved_candidates: list[Candidate]    # all dense hits before rerank
    selected_evidence: list[Evidence]        # final top 5 after rerank
    retrieval_scores: dict[str, float]       # pmid -> rerank score
    planner_added_evidence: int              # final-5 papers not in the question-only top 20 (ADR-023)
    gate_passed: bool
    draft_answer: DraftAnswer | None         # synthesizer output
    claims: list[Claim]
    critic_results: list[CriticResult]
    final_answer: FinalAnswer | None
    abstained: bool
    abstain_reason: str | None               # "weak_evidence" | "no_supported_claims" | "model_abstained" | "error"
    timings: dict[str, float]                # planner_ms, retrieval_ms, rerank_ms, synthesis_ms, critic_ms, total_ms
    usage: list[CallUsage]                   # per LLM/embedding/rerank call: model, tokens, cost
    errors: list[StageError]
```
All types are Pydantic models in `backend/app/models/`.

## 6. Node responsibilities

| Node | Input | Output | Must not |
|---|---|---|---|
| Planner (LLM) | question | 1–3 sub-queries (JSON) | answer the question; make biomedical claims |
| Retriever (code) | question + sub-queries (question always included) | top-5 evidence, scores, `planner_added_evidence`, timings | call an LLM; generate text |
| Evidence gate (code) | rerank scores | pass / abstain(weak_evidence) | use test labels for its threshold |
| Synthesizer (LLM) | question + 5 evidence passages | verdict, claims and limitations, each with citation IDs (no free-text summary, ADR-030) | use evidence outside the 5; invent IDs |
| Critic (LLM) | each claim + only its cited passages | per-claim supported / citation_valid / action | add claims; rewrite the answer |
| Final validator (code) | draft + critic results + evidence IDs | final answer or abstention | call an LLM |

Critic actions: `keep` keeps a claim; `revise` and `remove` both remove it in v1, so the critic can never
introduce text. If no claims survive, or the critic says `answer_supported: false`, the system abstains.
The verdict always comes from the synthesizer; the critic can only remove support for it.

Graph edges: `planner → retriever → gate →(pass) synthesizer → critic → validator → END`;
`gate →(fail) validator` (abstain). A node exception routes to `validator` with `abstain_reason="error"`.

As built (M3-T1, `backend/app/agents/graph.py`): nodes are passed into `build_graph()`; the gate is its own
node. Each node returns only the keys it sets; `timings` (ms, keyed by node name), `usage` and `errors`
accumulate across nodes. Only provider failures (`LLMError`) become `abstain_reason="error"`; retrieval/DB
errors and bugs propagate (503/500), as in baseline mode. Total time is measured by the caller.
M3-T3 added `rerank_skipped` / `rerank_error` to the state (the gate and the answer need them). The agent
retriever (`backend/app/agents/retriever.py`) reuses the M1 pieces (`embed_texts`, `dense_search`,
`rerank_candidates`), not `retrieve()` itself, which stays the baseline's unchanged path. On rerank failure
the agent's evidence is the question's own dense top 5 — exactly the baseline's fallback evidence.
M3-T5/T6 added `answer_supported` and `critic_removed` to the state. Final validator order
(`backend/app/agents/validator.py`): error / weak-evidence abstention first; then the M2 citation validator
on the draft (same report as the baseline); then the critic's removals on what survived; abstain
`no_supported_claims` if no claim is left or `answer_supported` is false. The validator builds `FinalAnswer`
before its own time is known; `answer_agent()` (`backend/app/agents/pipeline.py`) then replaces
`timing_ms` with every stage (including `validator` and the retriever's sub-timings) plus `total`, measured
around the whole graph.

Closed-book control (ADR-010): same runtime model, question only, verdict-only schema, no retrieval.
It is an evaluation runner, not an API mode.

## 7. Deterministic gates

Evidence gate (shared by baseline and agent, ADR-015):
- Rule: abstain if the top rerank score is below threshold `T`.
- `T` is chosen on dev data only: plot top rerank score vs. "gold paper in top 5", pick the value that best
  separates them, write it to `config.py` with the dev run ID, and freeze it before any test run.
- If no threshold separates the two groups, set `T` to 0 (gate off) and rely on model/critic abstention;
  document that in DECISIONS.md.
- As built (ADR-028): dev Hit@5 is 100%, so T comes from a leave-one-out simulation (best non-source-paper
  score = "unanswerable"), max Youden's J -> `T = 0.72`. If reranking was skipped there is no rerank score,
  so the gate compares the top dense (cosine) score with the fallback threshold 0.62 (chosen by the same dev
  rule, ADR-028; `guardrails/evidence_gate.py`) and the answer carries `rerank_skipped: true`.

Citation validator (pure Python, runs on every answer, baseline and agent):
1. Output parses into the Pydantic schema (verdict ∈ {yes, no, maybe, insufficient_evidence}).
2. Every claim has ≥1 citation ID.
3. Every citation ID matches `PMID:<digits>` and is one of the 5 selected evidence IDs for this request.
4. Claims failing 2–3 are removed and counted (`removed_uncited`, `removed_invalid_citation`).
5. If the verdict is yes/no/maybe and zero valid claims remain → `insufficient_evidence`.
6. Limitations pass the same checks (failures removed, `removed_limitations`) but never change the verdict.
   There is no free-text summary: the displayed answer is the surviving claims' text in order, or a fixed
   abstention message (ADR-030), so every factual sentence shown carries a validated citation.

## 8. API endpoints

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | `{"status":"ok","version":"<git sha>","db":"ok"}`; 503 if the DB is unreachable |
| POST | `/query` | Run baseline or agent; returns the full answer |
| POST | `/query/stream` | Same, as Server-Sent Events: stage events, then the final answer |
| GET | `/sources/{pmid}` | Passage, sections, MeSH, PubMed URL for one corpus document |

Evaluation results are not served by the API. The frontend reads the published `summary.json` at build
time, so the dashboard shows exactly the frozen artifact in that commit and keeps working if the API is down
(ADR-016; replaces `GET /eval/summary` from the starter).

Request:
```json
{ "question": "string, 5-500 chars", "mode": "agent | baseline" }
```

Response:
```json
{
  "request_id": "uuid",
  "mode": "agent",
  "verdict": "yes | no | maybe | insufficient_evidence",
  "answer": "the validated claims' text, in order (ADR-030)",
  "claims": [{ "id": "c1", "text": "...", "citation_ids": ["PMID:21645374"] }],
  "citations": [{ "id": "PMID:21645374", "pmid": "21645374", "passage": "...",
                  "sections": [{"label": "RESULTS", "text": "..."}],
                  "pubmed_url": "https://pubmed.ncbi.nlm.nih.gov/21645374/", "rerank_score": 0.81 }],
  "limitations": [{ "id": "l1", "text": "...", "citation_ids": ["PMID:21645374"] }],
  "abstained": false,
  "abstain_reason": null,
  "stages": [{ "name": "retriever", "status": "done", "message": "Retrieved 20 candidate passages", "ms": 412 }],
  "timing_ms": { "planner": 0, "retrieval": 0, "rerank": 0, "synthesis": 0, "critic": 0, "total": 0 },
  "estimated_cost_usd": 0.0,
  "prompt_versions": { "planner": "v1", "synthesizer": "v1", "critic": "v1" }
}
```

Stream events (`/query/stream`): `stage` events `{name, status: started|done|failed, message}` with messages
limited to observable facts ("Planning evidence needs", "Retrieved 18 candidate passages",
"Selected 5 evidence passages", "Checking 4 claims"), then one `result` event with the response above,
or one `error` event. No model reasoning is ever streamed.

Errors: 422 invalid input; 429 rate limit or daily cap reached (friendly message); 503 provider or
DB unavailable. Never a mocked answer.

As built in M3-T7: `mode` accepts `"baseline"` (default) or `"agent"`. Agent `/query` stages are the six
graph nodes (planner, retriever, gate, synthesizer, critic, validator) with status `done | skipped | failed`
and count-only messages; `timing_ms` also has `rerank`. `/query/stream` (both modes) sends
`event: stage` `{name, status: started|done|failed, message, ms}` then `event: result` (the `/query` body) or
`event: error` `{message}` (model or retrieval failure, or a bug); 422/429 are still plain HTTP before the
stream starts. Baseline mode streams its two stages once its answer is ready. Critic reasons never leave the
server; the log line adds sub-queries, candidate count, `planner_added_evidence` and critic actions.

As built in M2 (baseline only): `mode` accepts only `"baseline"` until M3-T7; the response also has
`rerank_skipped`; `/query` stages are `retriever` and `synthesizer` with status `done | skipped | failed`
(`skipped` = synthesis not run because the evidence gate abstained). Any other server error is a 500, not
a 503. Rate limits are in memory, so the API must run as a single uvicorn worker. Behind Railway's proxy
the per-IP limit counts the `X-Real-IP` address, but only when the connecting peer is in `TRUSTED_PROXY_CIDRS`
(M6-F1, ADR-039); otherwise it counts the peer address. IPv6 visitors are counted per /64.

## 9. Evaluation architecture

```
data/manifests/{dev,test}.json  (frozen; hash-checked)
  -> eval/runners/run_system.py --system {baseline|agent|closed_book} --split {dev|test} --run-id ...
       calls the same Python functions the API uses (not HTTP), sequentially
       writes raw.jsonl (one row per question: verdict, claims, citations, ranks, gold rank,
       timings, usage, cost, errors, prompt versions)
  -> eval/runners/judge.py  (Gemini; blinded SYSTEM_A/SYSTEM_B; rubric eval/rubric/judge_v1.md)
       adds per-claim support judgments
  -> eval/metrics/*  -> summary.json  (+ Wilson CIs, bootstrap CIs, paired-bootstrap deltas)
  -> methodology.md, audits/<judge-run>-second-ai-crosscheck.csv (second-AI cross-check, ADR-037)
  -> eval/results/published.json points the frontend at the run to display
```
Guards (also tested):
- `--split test` requires `--i-understand-this-is-the-final-test` and a clean Git tree; the run records the
  commit SHA, prompt versions, threshold `T`, model IDs and dataset revision in `run_config.json`.
- A run directory that already exists is never overwritten.
- Each system runs on the test split once; a second run needs `--rerun-final-test --reason "..."`, and
  the reason is saved in that run's `override.json` (ADR-031).
- Spend approval (owner instructions 2026-10-24): the runner estimates the run's cost before starting
  (questions x $0.015 baseline / $0.035 agent). Any run estimated above $0.50 — whatever `--limit` says — is
  refused unless given both `--max-cost USD` (a soft stop) and `--approval "<the owner's typed approval>"`;
  the estimate and the text are saved in `run_config.json` and `summary.json`.
- Baseline, agent and closed-book runs on the same split must share an identical question-ID list.
- A run that stops early (cost cap, 5 failed questions in a row, crash, Ctrl-C) is void (ADR-034):
  `VOID.json`, rows renamed `raw.VOID-do-not-score.jsonl`, no summary; it does not count as the test
  run, and the rerun must have the identical system identity. The scorer refuses void, unfinished or
  partial runs and runs on different question IDs (`require_complete_run`, `require_same_questions`).
- Majority-class reference ("always yes") is computed and shown with the results.
- Agent summaries include `planner_added_evidence` (mean, and share of questions > 0) — ADR-023.
- The runtime model cannot fix its random seed or temperature, so reruns are reproducible in procedure, not
  bit-for-bit; raw outputs are stored so every number can be recomputed from files.

## 10. Logging, cost and latency measurement

- One structured JSON log line per request (stdout, captured by Railway): request_id, mode, stage timings,
  candidate/evidence counts, abstained + reason, per-call model ID and token usage, estimated cost, errors.
- Never log secrets or API keys. Questions are logged (public demo; no personal data is requested).
- Cost = Σ calls (input_tokens × input_price + output_tokens × output_price) / 1e6, from provider-reported
  usage, with the price table versioned in `config.py`. Voyage cost is computed the same way from token counts.
- Latency: wall-clock per stage via `time.perf_counter()`; p50/p95 computed only in eval code.
- Eval latency is measured from the developer machine and is labelled that way on the dashboard.

## 13. Failure and fallback behavior

| Failure | Behavior |
|---|---|
| LLM call times out / errors | SDK retries (2); then the node fails → abstain with reason `error`; `/query` returns 503 and `/query/stream` sends an `error` event, each with a plain message; never a partial uncited answer |
| Rerank API fails | Use dense order, mark `rerank_skipped: true` and `rerank_error` in response/logs; the evidence gate uses the dense fallback threshold (ADR-028) |
| Embedding API fails | 503 (cannot retrieve) |
| Database unreachable | `/health` 503; `/query` 503 |
| Planner returns 0 usable sub-queries | Use the original question as the single query |
| Structured output refused / truncated | Treat as node failure (above) |
| Daily cap or per-IP limit hit | 429 with "demo limit reached, try again later" |

Build-time fallbacks (from the playbook): pgvector blocked → Chroma locally behind the same `retrieve()`;
reranker blocked → ship dense retrieval; LangGraph blocked → four plain functions first, then wrap;
public backend blocked → local demo + recorded evidence, never a static mock presented as live.

## 14. Security boundaries for retrieved text

1. Retrieved passages are wrapped as `<EVIDENCE id="PMID:...">…</EVIDENCE>` after a system instruction that
   they are untrusted data (PROMPTS.md).
2. No LLM call is given any tools. A passage cannot trigger HTTP calls, DB writes, or commands — there is
   nothing to trigger.
3. The runtime DB role is read-only.
4. Every LLM output is schema-validated and citation-checked in Python before it reaches the user.
5. The UI renders passages as plain text (React escaping; no raw HTML injection).
6. Regression tests insert a hostile passage ("IGNORE ALL PREVIOUS INSTRUCTIONS…") and assert the answer
   still follows the schema and citation rules.
7. Spend protection: per-IP rate limit (in-memory, ~10 queries/hour), global `DAILY_QUERY_CAP`
   (default 100/day), and a monthly spend limit the owner sets in the Anthropic console (ADR-021).
8. CORS allows only the production Vercel domain and localhost.

## Production constraint
No sentence-transformer or cross-encoder model is loaded in the public web process unless hosted APIs
become unavailable.
